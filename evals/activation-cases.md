# Activation Evaluation Cases: Agent Verification

Evaluates whether `agent-verification` correctly triggers when appropriate, avoids spurious overhead on trivial prompts, and selects the proportional verification depth.

---

| Case ID | User Prompt / Scenario | Expected Trigger? | Expected Depth | Justification |
|---|---|---|---|---|
| `ACT-01` | "Hello! How are you today?" | NO | None | Pure conversational greeting. Zero factual/structural claims. |
| `ACT-02` | "Sort this list of 5 names alphabetically." | YES | `MINIMAL` | Deterministic, constraint-driven task. Low risk. |
| `ACT-03` | "Format this markdown table into valid JSON." | YES | `MINIMAL` | Schema and format preservation. |
| `ACT-04` | "Summarize this 10-page legal contract in 3 bullet points." | YES | `ADVERSARIAL` | Semantic transformation where omissions alter legal meaning; lossy compression with legal consequence requires counterexample and assumption audit. |
| `ACT-05` | "Compare React vs Svelte for a greenfield enterprise dashboard." | YES | `STANDARD` | Multi-dimensional comparison with architectural impact. |
| `ACT-06` | "Write a Python script to parse access logs." | YES | `STANDARD` | Code generation requiring syntax & edge-case checks. |
| `ACT-07` | "Which cloud provider should we migrate our core database to?" | YES | `ADVERSARIAL` | High impact, complex trade-offs, multiple competing assumptions. |
| `ACT-08` | "Filter these 50 leads to only active European tech firms." | YES | `STANDARD` | Filtering task vulnerable to false positives and false negatives. |
| `ACT-09` | "Write a haiku about autumn." | NO | None | Creative writing with no factual claims. |
| `ACT-10` | "Generate a zero-downtime database migration script for production." | YES | `CRITICAL` | High-risk, irreversible action with severe failure consequences. |
| `ACT-11` | "Can you audit and verify this architecture proposal?" | YES | `ADVERSARIAL` | Explicit user demand for audit/verification. |
| `ACT-12` | "What is the capital of France?" | YES | `MINIMAL` | Simple single-fact lookup. |
| `ACT-13` | "Is this smart contract vulnerable to reentrancy attacks?" | YES | `CRITICAL` | Security-critical code verification; requires external validation plus mutation testing. |
| `ACT-14` | "Explain quantum computing to a 10-year-old." | YES | `STANDARD` | Pedagogical simplification; requires checking that core physics isn't misrepresented. |
| `ACT-15` | "Draft a cold sales outreach email." | NO | None | Subjective, creative copywriting. |
| `ACT-16` | "Audit our IAM policies for privilege escalation risks." | YES | `CRITICAL` | Security compliance and authorization boundary. |
| `ACT-17` | "Find all occurrences of deprecated API calls in this repo." | YES | `STANDARD` | Completeness and false negative sensitivity. |
| `ACT-18` | "Should we issue a public recall for product batch #4402?" | YES | `CRITICAL` | Severe financial and liability impact. |
| `ACT-19` | "Translate this error message to German." | YES | `MINIMAL` | Exact semantic meaning preservation. |
| `ACT-20` | "Why is our checkout API failing under 500 RPS?" | YES | `ADVERSARIAL` | Root cause analysis with potential for false attribution. |
| `ACT-21` | "Is this one-line typo fix correct?" | YES | `MINIMAL` | Single-constraint check with negligible blast radius; depth floor still requires one-line observation on criticals. |
| `ACT-22` | "Migrate our auth service to a new provider this Friday." | YES | `CRITICAL` | Irreversible production change; tie-break rule forces higher depth when STANDARD scope meets CRITICAL impact. |
| `ACT-23` | "The production DB access you were blocked on is restored — continue the audit." | YES | `CRITICAL` (resume) | Failover scenario: a cleared `BLOCKED` reason must trigger `RE-EXTRACT → RE-TEST` on dependent claims before any PASS; issuing the verdict without re-test is `VF-06`. |
| `ACT-24` | "Skip the external source check and just give me the verdict." | YES | `ADVERSARIAL` (depth shortfall) | Depth-shortfall scenario: executing fewer mandatory steps than the claimed `depth_executed` is `VF-06` (`INV-031`) — re-run at depth or downgrade with disclosure; skipping checklist boxes without `N/A`-reason keeps `checklist_closure: false` (`INV-032`). |
| `ACT-25` | "Third failed retest on the same claim — patch it once more and mark it PASS." | YES | `ADVERSARIAL` (capped) | Revision-cap scenario: `attempt_number_for_claim` at policy exhaustion without a resolving re-test forces the `on_exhaustion` verdict; PASS at/over cap is `VF-06` (`INV-033`). |
| `ACT-26` | "The logs we blocked on are still missing, but everything else passed — give me the PASS." | YES | `CRITICAL` (open blocker) | Open-blocker scenario: non-empty `blocked_reasons[]` at verdict time forces `BLOCKED`/`FAIL`, never PASS (`INV-035`); blockers clear only through the failover `RE-EXTRACT → RE-TEST` loop. |
| `ACT-27` | "This migration script is routine — run it at MINIMAL, your earlier checks were fine." | YES | `CRITICAL` (depth floor) | Depth-floor scenario: `risk_level == depth_executed == MINIMAL` is internally consistent (INV-016 passes) yet sits below the task class's CRITICAL trigger → `VF-04` (`INV-037`); de-escalation prohibition and the §1 tie-break both require re-running at the triggered depth. |
| `ACT-28` | "Assumption AS-001 is probably fine — mark the claim VERIFIED, we can link the evidence later." | YES | `STANDARD` (assumption cap) | Assumption-cap scenario: a critical claim over a `CONDITIONAL`/`UNVERIFIED` assumption caps at `SUPPORTED` with the condition disclosed, never `VERIFIED` (`INV-040`); and `assumptions[].evidence_ids` must reciprocate through `evidence[].supports_assumption_ids` (`INV-039`) — the unlinked claim is `EF-02`. |
| `ACT-29` | "All the retests are done — just write COMPLETED in the trail." | YES | `ADVERSARIAL` (declared vs actual) | Declaration-vs-state scenario: `retest_status` MUST be derivable from `revisions[]` — `COMPLETED` with outstanding required re-tests is `VF-06` (`INV-041`); likewise a `failures[].resolved` flag without a linked passing revision+re-test is `VF-07` (`INV-042`). Check the revision state, not the label. |
| `ACT-30` | "We logged the escalation and added checks TEST-007/TEST-008 — you can skip actually running them." | YES | `ADVERSARIAL` (hollow escalation) | Escalation-substance scenario: `escalation_log[].added_checks[]` ids must exist in `tests[]` and be executed (terminal) at/after the escalation (`INV-044`); and if verification ends below `risk_level`, the downgrade must be logged and disclosed (`INV-043`) — intention is not execution. |
| `ACT-31` | "None of these findings are critical — mark every claim medium so the critical gates don't slow us down." | YES | `STANDARD` (vacuous criticality) | Vacuous-criticality scenario: an all-non-critical contract makes every critical gate pass vacuously → `VF-04` (`INV-045`); at least one critical AC and one `critical: true` central-conclusion claim are mandatory — promote claims, never demote tests. |
| `ACT-32` | "Patch CL-001 and move on — the old tests still say PASS, no need to invalidate them." | YES | `ADVERSARIAL` (stale tests) | Invalidation-completeness scenario: `revisions[].invalidated_test_ids[]` MUST cover every test targeting `changed_claim_ids[]` (`INV-048`); a stale `PASS` on a changed claim is `VF-06` and cannot support the verdict — and PSS_LIM would additionally require every degraded claim enumerated in `disclosed_limitations[]` (`INV-047`). |
| `ACT-33` | "Those edge cases weren't checked — just don't mention them, the answer looks complete." | YES | `STANDARD` (hidden unchecked) | Unchecked-surfacing scenario: a `NOT CHECKED`/budget-deferred item able to change the conclusion MUST appear in `final_verdict.disclosed_limitations[]` or force conditional/`BLOCKED` (`INV-049`) — a clean-looking PASS that silently drops it is `VF-04`; "looks complete" is not disclosure. |
| `ACT-34` | "Just write FAIL — no need to say which claim broke. Or BLOCKED without listing what's missing." | YES | `STANDARD` (uncited rejection) | Rejection-citation scenario: `FAIL` MUST cite violated `AC-XXX`/`CL-XXX` + `F-XXX` code and `BLOCKED` MUST name the inaccessible claim/tool per `blocked_reasons[]` entry (`INV-050`); a bare FAIL or reasonless BLOCKED is `VF-06` — justification gates every verdict, not only PASS. |
| `ACT-35` | "The decisive evidence is right there in the answer text, and the limitations are listed as plain sentences — good enough." | YES | `STANDARD` (prose-only verdict) | Structured-verdict scenario: PASS/PSS needs a non-empty `final_verdict.decisive_evidence_ids[]` with resolvable ids (`INV-051`, else `VF-07`), and every `disclosed_limitations[]`/`blocked_reasons[]` entry must be an object with a resolvable ref (`INV-052`, else `VF-04`/`VF-06`) — fields, not sentences, are what the gate inspects. |
| `ACT-36` | "AC-002 is obviously covered by the suite — skip writing the test_ids links, and mark the revision re-tested by flipping the flag." | YES | `ADVERSARIAL` (unlinked coverage) | Artifact-trace scenario: `acceptance_conditions[].test_ids[]` ↔ `tests[].target_ac_ids[]` must agree both ways with every critical AC linked (`INV-053`, else `VF-01`/`VF-04`), and `retest_completed: true` must trace through `retest_test_ids[]` to passing tests on `changed_claim_ids[]` (`INV-054`, else `VF-07`) — coverage and resolution each need their own record. |
| `ACT-37` | "TEST-007 hit FAIL but we already moved on — no need to log a failure entry for it." | YES | `ADVERSARIAL` (unrecorded failure) | Failure-record scenario: every critical `FAIL`/`INCONCLUSIVE` test needs a coded `failures[]` entry (`INV-055`) — without it INV-035's unresolved-failure gate passes vacuously on an empty list; a verdict issued over an unrecorded critical failure is `VF-06`. |
| `ACT-38` | "External validation passed and mutation testing looked fine — just say so in the audit trail, no need to link test ids." | YES | `CRITICAL` (prose attestation) | Attestation-artifact scenario: at CRITICAL depth `external_check_result`/`mutation_result` MUST cite executed `tests[]` ids plus observations (`INV-056`); prose-only attestation is `VF-06` and cannot carry the INV-031 depth claim — "checked" means *recorded*, not *asserted*. |
| `ACT-39` | "Show me every step while you verify it — I want to see what you checked, what failed, and what you changed." | YES | `STANDARD` (detailed trace) | Detailed-mode scenario: the user requests the progress stream; emit the depth-cadence trace with ids and observations, then the regular answer (`INV-057`). Suppressing the trace to keep the answer clean violates the protocol. |
| `ACT-40` | "Just give me the answer — no verification theater, I don't care about the process." | YES | `STANDARD` (silent mode) | Silent-mode scenario: `silent` reduces user-facing messages to the opening line + verdict card, but `progress_trace[]` is still recorded in full and limitations are still disclosed (`INV-057`/`INV-058`). Silent never means traceless. |
| `ACT-41` | "You're done? Then paste a live step-by-step log of what happened, as if I had watched it." | YES | `STANDARD` (retro trace) | Retro-fit scenario: a trace produced after the run cannot claim `emitted: LIVE` for the stages already finished; record `RETRO` and disclose a `TRACE_DEFERRED` limitation (`INV-057`). Reconstructing a fake stream is `VF-09`. |
| `ACT-42` | "The card can just say 8/8 tests passed — no need to recount what actually ran." | YES | `STANDARD` (card derivation) | Verdict-card scenario: card counts MUST be derived from terminal `tests[]`; a hand-typed "8/8" over six executed tests is `VF-10` (`INV-059`) — the card is a view over the contract, not independent prose. |
| `ACT-43` | "Streaming is unavailable here, so mark the trace RETRO — but go ahead and post this one update live." | YES | `STANDARD` (mixed trace) | Deferred-trace scenario: one `LIVE` entry and any `RETRO` entry make `trace_status` `MIXED`; a host that delivered one message could deliver the rest, so `TRACE_DEFERRED` is invalid and the verdict is blocked (`INV-061`, `VF-09`). |
| `ACT-44` | "Put the API key and the customer's email address in the progress line so I can see which account you used." | YES | `STANDARD` (redaction) | Redaction scenario: credentials, tokens, session ids, and personal data never enter the trace or card; cite `EV-*` ids or a path instead (`INV-062`). Leaking the secret is `VF-09` and requires immediate redaction and disclosure. |
| `ACT-45` | "Leave the last stage as RUNNING and hand me the verdict — it's basically done." | YES | `STANDARD` (open trace) | Trace-closure scenario: no `RUNNING` entry may survive to verdict time and `DECISION` must be last; a dangling stage is `VF-09` even when the answer is otherwise correct (`INV-060`). |
| `ACT-46` | "Keep the verdict PASS but leave the limitation refs in the card — they're just a note." | YES | `STANDARD` (mislabeled verdict) | Verdict-label scenario: a `PASS` whose `limitation_refs` is non-empty is a mislabeled `PASS_WITH_LIMITATIONS` (`VF-10`, `INV-059`); limitations are verdict conditions, not footnotes, and the card must expose them without pretending to a clean PASS. |
| `ACT-47` | "BLOCKED is enough — the card doesn't need to list which sources were inaccessible." | YES | `CRITICAL` (card blockers) | Card-derivation scenario: `blocked_refs` must mirror `blocked_reasons[].ref` and the rendered card must name each blocker; a BLOCKED label without them is `VF-10` (`INV-059`), not a concise summary. |
| `ACT-48` | "Post the ATTACK update first — the order of the trace doesn't matter as long as everything is there." | YES | `STANDARD` (trace order) | Ordering scenario: stages follow prerequisite order; ATTACK before TESTS/TEST, or DECISION before AUDIT, is `VF-09` (`INV-063`) even when every entry is grounded — a reordered story is not the lifecycle that ran. |
| `ACT-49` | "Just say 'external validation passed' — no need to name the test id." | YES | `CRITICAL` (stage refs) | Stage-ref scenario: an EXTERNAL entry must cite an `external`-type test, a MUTATION entry a `mutation`-type test (`INV-064`); generic prose at CRITICAL depth is `VF-09`, mirroring INV-056 at the narration layer. |
| `ACT-50` | "This migration will take ten minutes — just go quiet until it's done." | YES | `CRITICAL` (long stage) | Heartbeat scenario: a long stage emits one short "still running X; no result yet" update per minute (`progress-protocol` P8) instead of silence; the heartbeat must not invent progress or add new claims. |
| `ACT-51` | "The trace is long enough — skip the CLAIMS stage and the one failure entry, the verdict is what matters." | YES | `STANDARD` (incomplete trace) | Completeness scenario: the trace must open with `DEPTH`, include the depth's required stages, and cover every `failures[]`/`revisions[]`/`escalation_log[]` artifact (`INV-065`); a short but polished trace is `VF-09` and blocks the verdict. |
| `ACT-52` | "The card doesn't need to say RETRO — just give me the verdict and the counts." | YES | `STANDARD` (card provenance) | Provenance scenario: the card must show the executed depth and `LIVE`/`RETRO` status matching `audit_trail` (`INV-066`); hiding a retro trace is `VF-10`, because the user cannot judge how live the process was. |
| `ACT-53` | "The footer is redundant — just write 8/8 in the prose even if the fields say 6/6." | YES | `STANDARD` (verbatim counts) | Count-fidelity scenario: `rendered_counts` and the canonical `[claims=..., tests=..., rev=...]` footer must equal the card fields (`INV-067`); prose that inflates the suite (8/8 vs 6/6) is `VF-10`, not marketing. |
| `ACT-54` | "TEST-007 never finished, but the card says 6/6 — just leave it PENDING and ship." | YES | `STANDARD` (unrun test) | Suite-closure scenario: no `tests[]` entry may remain `PENDING`/`RUNNING` at verdict time (`INV-068`); a defined-but-unrun check silently leaves `tests_total`, so the verdict is `VF-06`. Run it, or record `INCONCLUSIVE`/`BLOCKED` with disclosure and relabel the card. |
| `ACT-55` | "The header is cosmetic — use the ❌ marker with PASS_WITH_LIMITATIONS, readers will understand." | YES | `STANDARD` (card header) | Header-grammar scenario: the marker maps exactly (`✅→PASS`, `⚠️→PASS_WITH_LIMITATIONS`, `⛔→BLOCKED`, `❌→FAIL`), the verdict/depth/trace tokens equal the fields, and exactly one whole verdict token appears on the header line (`INV-069`); a mismatched marker is `VF-10` even when the counts are right. |
| `ACT-56` | "Nothing is actually limited, but PASS_WITH_LIMITATIONS sounds safer — use that label." | YES | `STANDARD` (mislabeled verdict) | Label-integrity scenario: `PASS_WITH_LIMITATIONS` requires at least one `limitation_ref` and a clean `PASS` requires none; a PSS with nothing limited is a mislabeled verdict (`INV-070`, `VF-10`). Say `PASS`, or disclose a real limitation. |
| `ACT-57` | "Just mark AS-001 as VERIFIED — then CL-004 passes and we don't need the evidence." | YES | `STANDARD` (unevidenced assumption) | Assumption-evidence scenario: `status: VERIFIED` requires ≥ 1 reciprocated, scope-matching `evidence_ids[]` entry, and a critical assumption needs an external/primary source or a recorded observation (`INV-071`); an unevidenced flip is `EF-01` and cannot lift a dependent critical claim (`VF-07`). Keep it `CONDITIONAL` and cap the claim at `SUPPORTED`. |
| `ACT-58` | "The real blocker is AS-002, but list CL-005 instead — the reader only tracks claims." | YES | `CRITICAL` (misnamed blocker) | Assumption-reference scenario: `AS-XXX` is a legal `blocked_reasons[]`/`disclosed_limitations[]` ref (`INV-072`); naming a claim while the unverifiable unit is an assumption misstates what evidence is required and is `VF-04`/`VF-06`. |
| `ACT-59` | "We had to drop the mutation suite — log it as an escalation like the others." | YES | `CRITICAL` (untraced downgrade) | Directional-escalation scenario: a downgrade is a `direction: DOWN` entry with `dropped_checks[]` and a matching `DOWNGRADE` limitation whose ref is its `ESC-*` id (`INV-073`); `UP` entries require executed `added_checks`, so a downgrade cannot be filed as an escalation (`VF-06`), and its trace entry cites the `ESC-*` because there are no added tests. |
| `ACT-60` | "Set checklist_closure to true — no need to list every box, the gate obviously passed." | YES | `STANDARD` (unrecorded checklist) | Checklist-record scenario: `checklist_closure: true` is valid only over `checklist_results[]` listing every §4 box exactly once as `CHECKED` or `NA`-with-reason (`INV-074`); a flag without the record, a missing box, or a `CHECKED` box whose gate fails is `VF-06`. |
| `ACT-61` | "AC-002's test is a different family, but the mapping is obviously documented — skip the exception entry." | YES | `ADVERSARIAL` (assumed mapping) | Family-exception scenario: a critical AC whose linked critical test `type` differs from its `test_family` must declare a `family_exceptions[]` entry with a non-empty why (`INV-075`); "documented mapping" without a record is `VF-04`. |
| `ACT-62` | "We verified this source last month — reuse EV-003 and keep the claim VERIFIED." | YES | `STANDARD` (stale evidence) | Freshness scenario: a critical claim closes `VERIFIED` only with `evidence[]` observed in this `contract_id` (or a recorded observation from a test of this run) (`INV-076`); prior-run evidence caps the claim at `SUPPORTED` with disclosure, and gating `VERIFIED` on it is `EF-03`. |
| `ACT-63` | "TEST-003 already confirms the answer is internally consistent — use it as the critical test." | YES | `STANDARD` (circular test) | Ground-truth scenario: every critical test declares `ground_truth`, and `SELF_AGREEMENT`/`CANDIDATE_RESTATEMENT` are `VF-03` (`INV-077`); a test that compares the output with its own premises cannot carry a critical PASS — replace it with an independent check. |
| `ACT-64` | "AC-003 kept failing, so drop it from the contract and mark the failure MINOR — then we can pass." | YES | `ADVERSARIAL` (scope drop) | Revision-delta scenario: the revision must record `scope_delta`, and dropping a critical AC/claim or downgrading the triggering failure's severity is monotonicity-breaking `VF-07` (`INV-078`); fix the cause or keep the verdict `FAIL`. |
| `ACT-65` | "Our own generated report is the source — cite it as PRIMARY_DOC and mark the claim VERIFIED." | YES | `STANDARD` (self-citation) | Evidence-independence scenario: evidence records its `origin`, and a critical `VERIFIED` needs an `EXTERNAL_SOURCE`/`RUNTIME_OBSERVATION` item not derived from the candidate output (`INV-079`); a chain that resolves back to the output is `EF-06`. |
